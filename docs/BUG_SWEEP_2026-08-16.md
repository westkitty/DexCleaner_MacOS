## 3. Complete bug ledger

### BUG-019: Preview expiry could leave destructive readiness looking current
- Status: fixed
- Severity: medium
- Location / affected area: `AppModel.canClean`, main cleanup action, confirmation sheet, menu-bar Preview status
- Evidence: authorization validity uses `Date()` and expires after fifteen minutes, but the original UI had no clock-driven state invalidation. With no unrelated state change, the disabled/enabled presentation could remain stale even though `cleanConfirmed()` would block the expired plan when invoked.
- Root cause: time-dependent authorization was represented by a computed property without a time-driven view refresh.
- Exact fix required: evaluate `canClean(at:)` and readiness text inside periodic `TimelineView` surfaces for the cleanup action, readiness callout, confirmation sheet, and menu-bar Preview status.
- Validation method: source inspection plus UI contract requiring `TimelineView(.periodic` and `PreviewAuthorization.maximumPlanAge`; live 15-minute macOS observation remains release QA.
- Fix result: applied.

### BUG-020: Scanner warnings and diagnostics were collected but hidden from the main UI
- Status: fixed
- Severity: medium
- Location / affected area: `ContentView`; AppModel state `storageSummaries`, `permissionDiagnostics`, and `warnings`
- Evidence: the model populated all three data sets from `ScanSnapshot`, and reports contained them, but the original `ContentView` did not render them.
- Root cause: report completeness advanced beyond interface completeness.
- Exact fix required: expose a progressive Scan Details surface with warnings, cleanable storage summaries, access-check status/detail/remediation, and the existing Access Settings action.
- Validation method: source inspection and UI contract tokens for all three sections; native visual/VoiceOver behavior remains macOS QA.
- Fix result: applied.

### BUG-021: Invalid additional audit exclusions were silently discarded
- Status: fixed
- Severity: medium
- Location / affected area: `AppModel.parsedExcludedRoots`, Reports & privacy exclusions UI
- Evidence: the original parser used `compactMap(ManifestValidator.canonicalRelativePath)`, safely ignoring invalid values but providing no indication to the user that an entered exclusion would not apply.
- Root cause: safety validation existed only at execution input, not at the configuration-feedback layer.
- Exact fix required: preserve the same canonical acceptance behavior while exposing accepted and rejected tokens through `exclusionInputValidation` and rendering ignored invalid entries in the UI.
- Validation method: source inspection and UI contract token for `exclusionInputValidation`.
- Fix result: applied.

### BUG-022: README release posture named a stale implementation branch
- Status: fixed
- Severity: low
- Location / affected area: `README.md`
- Evidence: the README said the safety refactor was implemented on `implement/adversarial-safety-refactor`, while the repository default branch is `main` and `main` contains the safety-refactor commit.
- Root cause: release documentation did not follow the branch integration.
- Exact fix required: describe the integrated `main` state and distinguish automated baseline evidence from still-unverified real-device release checks.
- Validation method: repository metadata check plus README review.
- Fix result: applied.
